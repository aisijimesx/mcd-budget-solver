# 30 块能吃什么

> 输入一个预算，帮你算出这个预算在麦当劳能吃到什么。
> 券不用你挑，算法替你穷举官方算价，预算内吃到最多。

## 它解决什么问题

你打开点单页面，面前是一堆优惠券和套餐组合。

- 满 20 减 6 和满 30 减 10 能一起用吗？
- 换成套餐更划算还是单点更划算？
- 到底该点哪几样，才能把这个预算花得最值？

这些问题不需要查资料，需要**穷举和试算**。这个项目把这件事交给算法。

输入「30 块能吃什么」，它会：

1. 领取你当前可领的全部优惠券
2. 读取你附近**有券的**门店此刻在售的菜单
3. 枚举商品与券的所有组合，逐组送官方算价工具试算
4. 在预算内选出**吃到最多东西**的那一组
5. 给你一张可以截图分享的今日战绩卡片

## 为什么不是"最便宜的方案"

这是这个项目最关键的一个设计决定。

如果目标函数写成「实付最低」，用户问「30 块能吃什么」会得到这样的答案：

```text
实付 5 元，吃到 1 样
方案：中可乐｜券：无门槛减 3
```

它在数学上是对的——5 元确实比 28 元便宜。但它是废话。

所以这个项目把**预算当作约束，把「吃到多少东西」当作目标**：

```text
效用 = 主食数量 + 配菜数量 × 0.6 + 套餐加权 + 偏好加权 + 预算利用率修正
```

金额只参与可行性判定和展示，不参与打分。实现在 `src/budget_solver.py` 的 `score_combo()`。

## 目标用户

- **常点麦当劳但没研究过凑单**的人。券囤了一堆，从没算过怎么用最划算。
- **预算有限的学生和上班族。** 30 块能吃到什么是个真问题。
- **想验证「便宜点单」技巧的人。** 想知道某个流传的说法到底省不省钱。

## 安装

### 前置条件

- Python 3.10 或更高
- 麦当劳 MCP Token（在`https://open.mcd.cn/mcp` 用手机号登录后申请）

### 安装 MCP

把 `mcp-config.example.json` 里的配置加到你的 MCP 客户端，替换其中的环境变量占位符：

```json
{
  "mcpServers": {
    "mcd-mcp": {
      "type": "streamablehttp",
      "url": "https://mcp.mcd.cn",
      "headers": {
        "Authorization": "Bearer ${MCD_MCP_TOKEN}"
      }
    }
  }
}
```

在 WorkBuddy 中：左侧边栏【专家·技能·连接器】→【连接器】→右上角【自定义连接器】→【配置MCP】，粘贴上述JSON 并把 `MCD_MCP_TOKEN` 换成你的实际Token，保存后启用。

### 安装技能

把 `SKILL.md` 与 `src/` 目录放入你的技能目录即可。

```bash
git clone <你的仓库地址>
cd mcd-budget-solver
python3 src/budget_solver.py
```

`budget_solver.py` 不联网，用桩数据演示求解逻辑。`mcd_adapter.py` 是真实
MCP 适配层，需要 Token 与网络：

```bash
export MCD_MCP_TOKEN=<你的token>
python3 src/mcd_adapter.py 广州
```

无第三方依赖，仅用 Python 标准库。

## 实现说明

核心逻辑三个文件，无第三方依赖：

| 文件 | 职责 |
| --- | --- |
| `src/mcd_adapter.py` | MCP 协议与数据映射，封装所有实测踩过的坑 |
| `src/budget_solver.py` | 候选生成、效用模型、战绩卡渲染 |
| `src/converge.py` | 两阶段收敛，把试算压到 24 次 |

**不自研优惠券叠加算法。** 所有金额计算都交给 MCP 的 `calculate-price` 完成。券的叠加规则、套餐替换规则、配送费口径都由官方服务定义，本地重算必然与服务端不一致。

### 核心：为什么不是"最便宜的方案"

这是这个项目最关键的一个设计决定。

如果目标函数写成「实付最低」，用户问「30 块能吃什么」会得到这样的答案：

```text
实付 5 元，吃到 1 样
方案：中可乐｜券：无门槛减 3
```

它在数学上是对的——5 元确实比 28 元便宜。但它是废话。

所以这个项目把**预算当作约束，把「吃到多少东西」当作目标**：

```text
效用 = Σ 单品权重 + 套餐加权 + 偏好加权 + 预算利用率修正

权重分档：
  套餐（三件套）  1.4   已含汉堡+小食+饮料，按整份计
  主食（汉堡类）  1.0
  小食（薯条等）  0.6
  未识别品类      0.3   刻意压低，避免误判为正餐
  饮料            0.2
  调料            0     完全不计
  无主食的组合   -1.5   重罚
```

金额只参与可行性判定和展示，不参与打分。实现在 `budget_solver.py` 的 `score_combo()`。

### 另一个坑：调料不算"吃到的东西"

调试时出现过这样的输出：

```text
实付 19.9 元，吃到 3 样小食
方案：麦咖啡™美式 + 韩式烟熏芝士风味酱 + 苹果片
```

两样"小食"是 3 元的酱料。按件数计数会显示"19.9 元吃到 3 样"，看起来很划算，
但用户看到的是一份酱料清单。

修正后：**调料权重为 0，且展示时降级为「配 N 样蘸料」不计入样数**。
同一个 30 元预算因此从"美式 + 酱料"变成"龙焰芝士棒鸡腿堡三件套，实付 29.9"。

### 关键约束：券是定向抵扣

实测确认，每张券的适用商品编码来自 `query-store-coupons`，且**只抵扣它指定的商品**：

| 组合 | 原价 | 优惠 | 实付 |
| --- | --- | --- | --- |
| 冰美式，无券 | 19.00 | 7.10 | 11.90 |
| 冰美式 + 券 | 19.00 | 9.10 | **9.90** |
| 巨无霸 + 冰美式 + 券 | 45.50 | 9.10 | **36.40** |
| 巨无霸 + 麦香鱼 + 冰美式 + 券 | 68.00 | 9.10 | **58.90** |

抵扣精确落在指定商品上，不影响同单其他商品。这个结构是收敛策略的基础——
含券的组合必然包含那个特定商品，枚举空间因此小一个数量级。

### 性能：24 次试算，8.6 秒

实测 `calculate-price` 单次往返约 0.34 秒，朴素枚举 120 次意味着 40 秒等待，
对交互式 Skill 不可接受。

利用「券只能挂在特定商品上」这个约束做两阶段收敛：

1. **阶段一：无券基准。** 枚举 10 组，找到不靠券时预算内能吃最好的方案。
2. **阶段二：含券组合。** 以每张券的适用商品为种子向外组合配菜，
   只保留券前原价不超过预算 1.3 倍的候选。

| 指标 | 朴素枚举 | 分阶段收敛 |
| --- | --- | --- |
| 候选组合 | 数千 | 31 |
| 实际试算 | 120 | **24** |
| 耗时 | 40+ 秒 | **8.6 秒** |

```text
用户诉求 + 城市
  ↓
pick_stores_with_coupons    遍历门店找到有券的（实测券数因店而异，0~3 张）
  ↓
auto-bind-coupons           一键领券
  ↓
get_menu                    当前门店在售菜单
  ↓
阶段一：无券基准（10 组）
  ↓
阶段二：含券组合（21 组，以券的适用商品为种子）
  ↓
calculate-price × 24        逐组官方试算
  ↓
score_combo 排序            预算内效用最高者胜出
  ↓
战绩卡片 + 下单确认
```

## 边界与限制

- **不承诺库存。** 菜单接口返回的是当前在售，但不返回实时库存，售罄请以官方渠道为准。
- **不涉及线下排队和出餐时长。** 这类数据 MCP 没有，本项目不做推断。
- **账户券无法用于算价。** `query-my-coupons` 只返回文本，不含券 ID。券枚举只依赖门店券。
- **券数因店而异。** 实测同城不同门店券数从 0 到 3 张不等，需遍历查找。
- **领券会修改你的账户。** 所以流程会先询问再调用。
- **不会自动下单。** 任何情况下都需要你明确确认。
- **换门店要重新拉菜单。** 菜单是门店实时数据，不跨门店复用。
